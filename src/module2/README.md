# Модуль 2. Аналитическое ядро: спектральные индексы и сегментация стресса

Вход: многоканальные GeoTIFF-сцены (`scene_YYYY_MM_DD.tif`, отражение, по одной на дату).
Выход: маски зон `zones_YYYY_MM_DD.tif` (0 фон, 1 сильный стресс, 2 умеренный, 3 норма), файлы индексов,
`index_stats_YYYY_MM_DD.json` на каждую дату (для дашборда M4) и сводный `indices_summary.json`.

## Запуск

Команды выполняются из папки `src/module2` (рядом с `stress_core/`).

```bash
pip install -r requirements.txt     # numpy, scipy, scikit-learn, tifffile, imagecodecs, matplotlib, spyndex

# серия сцен -> data/zones, data/stats, data/indices, data/hidden_stress
python -m stress_core run ../../data/scenes -o ../../data

# новые сцены; уже обработанные даты пропускаются, если их не передать в --reprocess
python -m stress_core update ../../data/scenes -o ../../data

# проверить результаты на контракт с M3 и M4 (классы 0..3, одна сетка, площадь поля на всех датах)
python -m stress_core check ../../data

# маски и графики за сезон -> data/season (КТ4)
python -m stress_core season ../../data

# одна сцена: каналы и дата берутся из файла (у sample_scene.tif дата записана в метаданных)
python -m stress_core run ../../data/samples/sample_scene.tif -o out

# только индексы одной сцены: NDVI.tif, NDRE.tif, MSAVI.tif, NDMI.tif
python -m stress_core indices ../../data/samples/sample_scene.tif -o out_indices

# демо на синтетическом поле (3 даты)
python -m stress_core demo -o demo_out
```

Папки `out`, `out_indices`, `demo_out` не коммитьте: это результаты запуска.

**Каналы** определяются по файлу: по описаниям B02…B12, которые пишет M1; без описаний 10 каналов считаются форматом M1
(`B,G,R,RE1,RE2,RE3,N,N2,S1,S2`), 4 канала — `R,RE1,N,S1`. Вручную: `--bands s2-10` или имена ASI через запятую.
Если заданный порядок не совпадает с числом каналов или с описаниями в файле, это ошибка (перепутанные каналы иначе
молча дали бы неверные индексы). **Дата** берётся из `--date`, иначе из имени файла, иначе из тега `date` в метаданных.
`--classes 3|4|5|auto`, по умолчанию 3 (контракт M2 -> M3).

Тесты: `python -m unittest discover -s tests -v` (из `src/module2`).

## Интеграция в общий пайплайн (для `main_pipeline.py` модуля 1)

После того как M1 докачал сцены в `data/scenes/`, достаточно одного вызова: он обработает только новые даты. `main_pipeline.py` сам передаёт в `reprocess=` подменённые (по sha256) и запоздавшие даты — см. пункт «Вызов из `main_pipeline.py`» ниже.

```python
from stress_core import process_new_scenes

res = process_new_scenes("data/scenes")      # результаты в data/ (zones, stats, indices, hidden_stress)
# res["processed"] — посчитанные даты, передать дальше в M3; res["errors"] — даты с ошибкой
```

Для одной конкретной сцены:

```python
from stress_core import analyze_field

rec = analyze_field("data/scenes/scene_2026_08_14.tif")
# -> data/zones/zones_2026_08_14.tif, data/stats/index_stats_2026_08_14.json, data/indices/*, data/hidden_stress/*
```

- **Повторный запуск безопасен.** Дата считается обработанной, если есть и `stats/index_stats_*.json`, и `zones/zones_*.tif`; без новых снимков `process_new_scenes` ничего не меняет. Если пришла сцена с датой раньше уже обработанной, она обрабатывается, но в `warnings` будет совет перезапустить всю серию (`run`): динамика более поздних дат посчитана без неё. Так ведёт себя прямой вызов без `reprocess`; как работает `main_pipeline.py` — ниже.
- **Перекачанная сцена.** Если M1 перекачал сцену (`s2fetch --force`), а результат за эту дату уже есть, `process_new_scenes` её не трогает. Если файл сцены новее своего `stats`-файла, выдаётся предупреждение (в `warnings`), но заново дата не обрабатывается. Обработать заново:

  ```python
  res = process_new_scenes("data/scenes", reprocess=["2026-06-20"])
  # res["processed"] — все посчитанные даты (новые и заново), res["reprocessed"] — те, где результат уже был
  ```

  или `python -m stress_core update data/scenes -o data --reprocess 2026-06-20 [ДАТА ...]`. `--reprocess` ставить после папки сцен: он принимает несколько дат и иначе примет папку за дату.
  Динамика и правило decline зависят от предыдущей даты, поэтому вместе с самой ранней датой из `reprocess` пересчитываются **все более поздние уже обработанные даты**: результат совпадает с полным `run` (проверено тестом). Если сцены какой-то из этих более поздних дат нет во входных данных, её пересчитать нельзя, и в `warnings` будет совет перезапустить всю серию. Если переобработка даты упала (например, файл сцены битый), на диске остаются её прежние zones и stats, а в `warnings` перечислены более поздние даты, динамика которых посчитана от этого прежнего результата.

  Предупреждение «сцена новее результата» основано на времени изменения файла, а не на содержимом: после `git pull`, `git checkout` или копирования `data/scenes` оно появится и для неизменённых сцен. Если сцены не перекачивались, его можно не учитывать. Надёжная проверка — по sha256 в `main_pipeline.py`.

  После `--reprocess` стоит запустить `python -m stress_core check data`: перекачанная сцена может прийти с другой сеткой или CRS, а M3 требует одну сетку на всех датах, и пересчёт её не выравнивает.

- **Вызов из `main_pipeline.py`.** Подмену сцен он отслеживает по sha256: подменённые даты и новые даты раньше уже обработанных передаёт в `reprocess`, а всю серию заново считает только с `--rebuild`.
  Известное ограничение: если самая ранняя дата из `reprocess` ещё не была обработана, в `warnings` всё равно появляется совет перезапустить всю серию («раньше уже обработанной…»), хотя все более поздние даты уже пересчитаны. При вызове с `reprocess` это предупреждение ложное; `main_pipeline.py` переносит его в `info` отчёта, если все более поздние даты пересчитались.
- **Куда пишет.** Для сцены из `data/scenes/` результаты по умолчанию ложатся в `data/` (раскладка из плана); можно передать папку вторым аргументом.
- **Динамика между датами.** Если в `data/indices/` уже лежат результаты более ранней даты, `analyze_field` сравнивает новую сцену с ближайшей предыдущей (дата сравнения записана в `early_stress.compared_with`; `null`, если сравнивать не с чем или сетка другая). Результат совпадает с обработкой всей серии за один запуск (проверено тестом).
- **Серия целиком:** `python -m stress_core run data/scenes -o data`. Файлы без даты и повторы даты пропускаются с предупреждением (список в `indices_summary.json`, поле `warnings`). Флаг `--no-history` отключает сравнение первой сцены с уже имеющимися результатами.
- `indices_summary.json` дополняется: даты, обработанные в прошлых запусках, сохраняются.
- Ошибка в одной сцене не останавливает серию: в `indices_summary.json` у даты будет поле `error`; `analyze_field` для одной сцены при ошибке выбрасывает `RuntimeError`.

## Контракт входа

- GeoTIFF; uint16 = отражение ×10000, float32 = отражение 0..1 (как в плане M1). Если float-значения явно больше 1 (не нормированы), делитель 10000 выбирается сам; вручную `--scale`. Выбранные порядок каналов и делитель записываются в `index_stats` (поле `input`).
- Сжатие: deflate/zstd или без сжатия читаются всегда; LZW, JPEG и float-предиктор требуют `imagecodecs` (есть в `requirements.txt`).
- Как у M1: вне поля во всех каналах nodata (0), облака и тени внутри поля — NaN. Контур поля — пиксели, где не все каналы равны nodata; он берётся из каждой сцены и должен совпадать на всех датах. Если nodata в файле не задан или сам NaN, «вне поля» и «облако» не различить, и контуром считаются пиксели с данными. Валиден пиксель, где все нужные каналы конечны и `0 < отражение <= 1.5`.
- Все каналы на одной сетке 10 м (ресемплинг — задача M1), CRS проекционная в метрах (UTM), иначе `area_ha` будет `null`. Для сравнения дат сетка должна совпадать.

## Контракт выхода (`<out>/`)

| Файл | Содержимое |
|---|---|
| `zones/zones_YYYY_MM_DD.tif` | uint8: `0` вне поля, `1` сильный стресс (худший по NDRE), `2` умеренный, `3` норма. Покрывает весь контур поля на любой дате: облачные пиксели получают класс ближайшей зоны. Для M3 нужны 3 класса (по умолчанию) |
| `stats/index_stats_YYYY_MM_DD.json` | статистика даты и `early_stress_alert` (см. ниже) |
| `indices/NDVI_YYYY_MM_DD.tif` (+ `NDRE`, `MSAVI`, `NDMI`) | одноканальные float32, NaN = нет данных (вне поля или облако; значения под облаком не досчитываются) |
| `hidden_stress/hidden_stress_YYYY_MM_DD.tif` | uint8: `1` скрытый стресс, `0` нет, `255` нет данных (вне поля или облако) |
| `indices_summary.json` | то же по всем датам, плюс конфигурация запуска и предупреждения |
| `season/season_*.png`, `season/season_report.json` | после `season`: маски зон, карты NDVI/NDRE и графики динамики за сезон, опережение Red Edge |

Геопривязка (CRS, шаг, начало координат) копируется из входной сцены.

**`index_stats_YYYY_MM_DD.json`.** Поля для дашборда: `date`, `mean_ndvi`, `mean_ndre`, `mean_msavi`, `mean_ndmi`,
`early_stress_alert` (bool), `early_stress_area_ha`, `early_stress_percent`, `field_area_ha` (весь контур, одинакова на всех датах),
`observed_area_ha` (с данными), `filled_area_ha` и `filled_percent` (облако/тень, класс зоны восстановлен по соседям). Дополнительно: `grid`, `valid_pixels`, `field_pixels`, `filled_pixels`,
`warnings` (если без данных больше 20% поля), `indices.<имя>` (`n, mean, std, min, max, p5…p95`), `zones` (`n_classes`, `classes[]` с `class, label, pixels, fraction, area_ha, filled_pixels, filled_area_ha, mean{индекс}`),
`hidden_stress`, `early_stress` (`alert`, `reasons`, `ndre_drop`, `ndvi_drop`, `common_fraction`, `compared_with`), `input` (`band_order`, `band_names_in_file`, `scale`, `dtype`), `files`.
`mean_*` — средние по пикселям поля с данными на эту дату; `early_stress_percent` — доля от `observed_area_ha`; `ndre_drop`/`ndvi_drop` — изменение относительно прошлой даты по пикселям, видимым на обеих датах.

## Как это работает

1. **Индексы** (`indices.py`): NDVI, NDRE, MSAVI2 (в файлах и ключах `MSAVI` / `mean_msavi`), NDMI по формулам каталога Awesome Spectral Indices; значения сверены со spyndex тестом `test_matches_spyndex`.
2. **Скрытый стресс** (`early_stress.py`), три правила, площадь каждого — в `hidden_stress.by_rule_ha`:
   - `spatial` (одна дата): NDRE и NDVI сглаживаются (σ=1 px), переводятся в робастный z-score относительно самого поля; флаг — NDRE заметно ниже нормы (`z <= -1.5`) при ещё нормальном NDVI (`z > -1.0`);
   - `temporal` (есть прошлая дата): резкое падение z-аномалии NDRE при почти неизменной аномалии NDVI — внезапный очаг;
   - `decline` (есть прошлая дата): NDRE в пикселе действительно упал, причём на 4 п.п. и больше сильнее медианы поля, и это сверх-падение в 1,5 раза больше, чем у NDVI. Ловит постепенное угнетение участка, которое z-правила пропускают (см. калибровку ниже).

   Мелкие пятна (< 12 px) убираются.
3. **`early_stress_alert`**: `true`, если скрытый стресс занимает не менее 1% поля, либо (при наличии прошлой даты) NDRE упал минимум на 0.02 и относительно быстрее NDVI в 1.5 раза и более. Падение считается только по пикселям, видимым на обеих датах (облако на одной из дат иначе сдвигает среднее и даёт ложную тревогу); если таких пикселей меньше 50%, динамика не оценивается. Пороги в `EarlyStressConfig`.
4. **Зоны** (`zoning.py`): признаки (NDVI, NDRE, MSAVI2, NDMI) сглаживаются и стандартизируются, KMeans (k задан или по силуэту в 3–5), классы сортируются по среднему NDRE (1 — самый низкий), затем мажоритарный фильтр (как `median_filter` в ТЗ, но для меток классов) и слияние пятен < 25 px с соседом.
5. **Края поля.** Пиксели на границе поля и у дыр от облаков смешанные (часть пикселя занимает дорога или соседний объект) и выглядят как ложный стресс. Пояс шириной `edge_buffer_px` (по умолчанию 1 px) не участвует ни в кластеризации, ни в поиске скрытого стресса. В маске зон такие пиксели получают класс ближайшей зоны, поэтому контур и площадь поля не меняются. Отключается `edge_buffer_px=0` в `ZoningConfig` и `EarlyStressConfig`. Статистика индексов в JSON по-прежнему считается по всем пикселям поля.

6. **Облачные дыры.** Пиксели внутри контура без данных не кластеризуются, а в маске зон получают класс ближайшей зоны (как краевой пояс). Так площадь зон равна площади поля на всех датах и проверка стабильности площади в M3 проходит. Индексы и скрытый стресс под облаком остаются «нет данных». Площадь заполненного — `filled_area_ha` (всего и по классам); при доле больше 20% в JSON появляется `warnings`: зонам там доверять меньше.

## Калибровка на сезоне 2026 (КТ4)

Серия M1: 8 дат с 3 июля по 24 августа, поле 79,6 га. С середины августа созревает всё поле, к 24 августа NDVI падает на 0,10–0,23; сильнее всего — на юге.

- Старое временное правило (`temporal`, порог по z-аномалиям) на реальной серии почти не срабатывало: спад постепенный и захватывает широкий участок, а пороги подбирались на синтетике с резким очагом. Поэтому добавлено правило `decline`.
- Проверка без подгонки «на глаз»: для каждой даты отмеченные пиксели сравнивались с худшей четвертью поля по дальнейшему падению NDVI к 24 августа (случайный выбор попадает в неё в 25 % случаев). При пороге 0,04 точность 83 % на 7 августа (5,4 га) и 95 % на 14 августа (4,3 га); ложное срабатывание — 1 га 28 июля; на 8 июля без условия «NDRE действительно упал» правило давало ложные 6 га в фазе роста — условие добавлено.
- Итог (`python -m stress_core season data`): очаг 7 августа (5,5 га) в этот день имеет NDRE на 9 % ниже поля при NDVI на 5 %; NDVI отстаёт от поля на 10 % только 17 августа, на 21 % — 24 августа. **Опережение Red Edge — 10 дней** (до обвала — 17 дней). Тревоги: 18 и 28 июля (пятно на северо-востоке), 7 и 14 августа (юг).
- Подробный разбор и картинки: `docs/module2_season_2026.md`.

## Ограничения и допущения

- **Зоны относительные.** Класс 1 — «хуже остального поля на эту дату», а не абсолютный порог. На здоровом поле алгоритм всё равно выделит классы из-за неоднородности почвы, поэтому подписи читайте вместе со средними индексами класса. Смысл номера класса между датами не гарантирован.
- **Скрытый стресс тоже относительный:** если угнетена больше половины поля, медиана смещается и метод занижает очаги.
- Пороги правила `decline` подобраны на одном поле и одном сезоне (2026, 8 дат) по совпадению с последующим обвалом NDVI, полевой разметки (что это было — болезнь, засуха, неравномерное созревание) нет. Северо-восточное пятно 18–28 июля, по данным M1, скорее другая фаза развития посева, а не стресс; отметки вдоль колеи дождевальной машины — постоянный объект. На другом поле или культуре пороги нужно проверять заново (`python -m stress_core season`).
- Пояс шириной 1 px по краю поля не классифицируется сам, а наследует класс соседей: реальный очаг шириной в один пиксель у самой границы будет сглажен.
- Xarray и rasterio не используются: расчёт на NumPy, GeoTIFF через tifffile. Повёрнутые растры (ModelTransformation без шага пикселя) читаются, но площадь для них не считается.
- Основной расчёт индексов — NumPy. Пакет `spyndex` входит в `requirements.txt`: он нужен для бэкенда `--backend spyndex` и для теста `test_matches_spyndex`, который сверяет формулы NumPy со spyndex. Если пакет не установлен, расчёт работает, а этот тест пропускается.
