# Модуль 3. Карты-предписания VRA и экономика

Ответственный по плану проекта: **Кузнецов Кирилл**.

Модуль переводит маску зон из Модуля 2 в полигоны, назначает нормы внесения,
сохраняет GeoJSON и комплект ESRI Shapefile в ZIP, рассчитывает площади,
расход препарата и экономию относительно сплошной обработки.

## Быстрый запуск

Нужен Python 3.11 или новее. Команды ниже выполняются из корня репозитория с установленными
зависимостями. Рекомендуется отдельное виртуальное окружение:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r src/module3/requirements.txt
python -m pip install -e src/module3

# Обработать оба эталона из архива проекта
python src/module3/examples/run_samples.py

# Запустить проверки
python -m unittest discover -s src/module3/tests -v
```

Примеры сохраняются отдельно в `data/module3_demo/sample/` и
`data/module3_demo/module2/`, чтобы две маски одной даты не перезаписали друг друга.

Для одного файла:

```powershell
python -m vra run data/samples/sample_zones_m2.tif -o data/prescriptions --date 2026-08-07
```

Если пакет не установлен через `pip install -e`, можно перейти в `src/module3`
и выполнять `python -m vra`, указав пути относительно этой папки:

```powershell
cd src/module3
python -m vra run ../../data/samples/sample_zones_m2.tif -o ../../data/prescriptions --date 2026-08-07
```

## Параметры обработки

```powershell
python -m vra run data/zones -o data/prescriptions --base-rate 150 --price 45 --rates "1=150,2=80,3=0" --min-area 0.05
```

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `INPUT` | GeoTIFF или папка с файлами `zones_YYYY_MM_DD.tif` | Обязателен |
| `-o`, `--output` | Папка результата | Обязателен |
| `--date` | Дата одиночного файла без даты в имени | Из имени файла |
| `--base-rate` | Норма для сравнения со сплошным внесением | `150` |
| `--price` | Цена единицы препарата, руб./кг или руб./л | `45` |
| `--rates` | Нормы по классам в кг/га или л/га | `1=150,2=80,3=0` |
| `--min-area` | Порог объединения малых полигонов, га | `0.05` |
| `--unit` | Единица количества: `kg` или `l` | `kg` |
| `--area-tolerance-ha` | Допустимый разброс площади между датами, га | `0.01` |

Нормы, цена и порог площади должны быть конечными неотрицательными числами.
Изменение `--base-rate` меняет сценарий сплошной обработки; нормы VRA задаются
отдельно через `--rates`. Цена влияет на денежную экономию, но не на геометрию
или количество препарата. `--min-area 0` отключает объединение малых контуров.

Для жидкого препарата:

```powershell
python -m vra run data/samples/sample_zones_m2.tif -o data/liquid_prescriptions --date 2026-08-07 --unit l --base-rate 2 --price 800 --rates "1=2,2=1,3=0"
```

В режиме `l` нормы и количество выражены в литрах. Перевода килограммов в литры
нет: для такого перевода нужна плотность конкретного препарата. Интерфейс Модуля 4
из исходного ТЗ ожидает килограммы, поэтому для него используйте стандартный
режим `kg` либо добавьте отображение единицы из отчёта.

## Вход М2 → М3

Нужен одноканальный GeoTIFF с геопривязкой и указанной CRS:

| Значение | Назначение |
|---|---|
| `0` | Фон / нет данных; не входит в обрабатываемую площадь |
| `1` | Острый стресс |
| `2` | Умеренное угнетение |
| `3` | Норма |

Также исключаются пиксели, замаскированные средствами GeoTIFF, и значения nodata.
Неизвестные классы и дробные номера классов отклоняются: их нельзя молча
отбросить и тем самым занизить площадь. Полностью пустая маска не создаёт
предписание. Для Модуля 2 используйте режим трёх классов, как требует общий
контракт проекта; его варианты на четыре или пять классов сюда не подходят.

Поддерживаются географические и проекционные системы координат. Если вход уже
в UTM, используется эта метрическая система. Для остальных CRS определяется
локальная UTM; для полярных полей предусмотрена локальная равновеликая проекция
LAEA. Площадь вычисляется в квадратных метрах и делится на 10 000. Квадратные
градусы или квадратные футы не принимаются за квадратные метры.

В архиве проекта имеются два разных эталона:

- `sample_zones.tif` — тестовое разбиение по терцилям NDVI, а не подтверждённая
  карта заболеваний.
- `sample_zones_m2.tif` — маска, подготовленная аналитическим модулем; классы
  описывают относительное состояние растительности.

Дата исходной сцены по `data/README.md` — **2026-08-07**, CRS — EPSG:32637,
пиксель — 10 × 10 м. Две маски одной сцены не являются двумя неделями сезона.

## Результаты М3 → М4

В папке результата для каждой даты создаются:

```text
prescription_YYYY_MM_DD.geojson
shapefile_YYYY_MM_DD.zip
metrics_YYYY_MM_DD.json
```

GeoJSON имеет координаты EPSG:4326 — долгота, широта. Для каждого полигона
передаются `zone_class`, `zone_name`, `area_ha` и `fertilizer_rate`.
В стандартном режиме `kg` также есть `rate_kg_ha`, который ожидает подсказка
на карте из ТЗ Модуля 4. Значения `fertilizer_rate` и `rate_kg_ha` совпадают.

ZIP содержит согласованный комплект `.shp`, `.shx`, `.dbf`, `.prj` и `.cpg`.
Короткие имена атрибутов Shapefile учитывают ограничения DBF; CRS записана в
`.prj`, кодировка — в `.cpg`. Для переноса используйте весь ZIP, а не один `.shp`.
Распакованный комплект также остаётся в папке `shapefile_YYYY_MM_DD/`.
Короткие соответствия полей: `fert_rate` = `fertilizer_rate`,
`total_qty` = `total_quantity`, `qty_unit` = `quantity_unit`.

Основные поля `metrics_YYYY_MM_DD.json` в режиме `kg`:

| Поле | Содержание |
|---|---|
| `date` | Дата расчёта |
| `total_field_area_ha` | Сумма площадей валидных классов, га |
| `stressed_area_ha` | Площадь классов 1 и 2 на карте-предписании, га |
| `stressed_area_percent` | Доля классов 1 и 2, % |
| `uniform_application_kg` | Расход при сплошном внесении, кг |
| `smart_application_kg` | Расход по карте VRA, кг |
| `saved_fertilizer_kg` | Разница расходов, кг |
| `saved_percent` | Разница расходов относительно сплошного внесения, % |
| `saved_money_rub` | Разница стоимости препарата, руб. |
| `zone_breakdown` | Площади, доли, нормы и расход по каждому классу |
| `processing` | Сведения о векторизации, CRS и объединении контуров |

Разбивка включает все три класса, в том числе отсутствующий на конкретной
маске класс с нулевой площадью. Она подходит для круговой диаграммы в Модуле 4.
Экономика считается по фактически экспортированным зонам после объединения
мелких контуров.

В `processing` сохраняются:

- `source_area_by_zone`, `source_stressed_area_ha`, `source_stressed_area_percent`,
  `source_total_field_area_ha` — исходные площади до объединения;
- `input_polygon_count`, `output_polygon_count`, `merged_polygon_count`,
  `retained_small_polygon_count` — количество контуров и результат фильтрации;
- `reassigned_area_ha` — площадь, которой при объединении изменили класс;
- `min_polygon_area_ha`, `source_crs`, `area_crs`, `valid_pixel_count`,
  `excluded_pixel_count` — параметры и характеристики входа.

Для кода, работающего с обеими единицами, предназначены общие поля
`uniform_application_quantity`, `smart_application_quantity`, `saved_quantity`,
`quantity_unit` и `rate_unit`. Килограммовые поля присутствуют в режиме `kg`;
в режиме `l` используются соответствующие поля с суффиксом `_l`.

## Как обрабатываются малые полигоны

`rasterio.features.shapes` выделяет связные области классов. Контуры менее
`0.05` га объединяются с соседним полигоном по общей границе, сохраняя общую
площадь и внешний контур поля. Объединённый участок наследует класс и норму
соседа. Это может изменить площадь отдельных классов и расход препарата;
исходная и итоговая статистика позволяют оценить такое изменение.

Изолированный малый островок без общей границы с другим полигоном сохраняется
и отмечается в отчёте. Его удаление исказило бы площадь поля. Отверстия nodata
не заполняются, а полигоны не соединяются через фон. Это ограничение означает,
что порог `0.05` га не гарантирует отсутствие всех малых островков на выходе.

## Формулы экономики

Пусть `Aᵢ` — площадь зоны класса `i` в гектарах, `rᵢ` — её норма,
`b` — базовая норма сплошного внесения, `p` — цена единицы препарата.

```text
A = A₁ + A₂ + A₃
Площадь зон стресса = A₁ + A₂
Доля зон стресса = (A₁ + A₂) / A × 100%
Расход при сплошном внесении = A × b
Расход VRA = A₁ × r₁ + A₂ × r₂ + A₃ × r₃
Экономия препарата = расход при сплошном внесении − расход VRA
Экономия денег = экономия препарата × p
Экономия, % = экономия препарата / расход при сплошном внесении × 100%
```

Расчёт использует площади до округления для отображения. Отрицательная
экономия означает перерасход; он не обрезается до нуля. Это позволяет корректно
сравнивать сценарии, где нормы VRA выше выбранной базовой нормы.
Если базовый расход равен нулю, `saved_percent` имеет значение `null`:
процент относительно нулевой базы не определён. Количество и деньги при этом рассчитываются.

Денежный показатель учитывает только стоимость препарата. Он не включает
топливо, труд, оборудование, логистику или изменение урожайности и не является
полной оценкой прибыли хозяйства.

## Python API

```python
from vra import calculate_economics, generate_prescription

geojson, shapefile_zip, metrics = generate_prescription(
    zones_tif_path="data/samples/sample_zones_m2.tif",
    output_dir="data/prescriptions",
    date_str="2026-08-07",  # также принимается 2026_08_07
    base_rate_kg_ha=150.0,
    rates_by_zone={1: 150.0, 2: 80.0, 3: 0.0},
    price_per_kg=45.0,
    min_polygon_area_ha=0.05,
    unit="kg",
)

# Пересчёт экономики без повторной векторизации, например для слайдеров М4
report = calculate_economics(
    area_by_zone={1: 10.0, 2: 20.0, 3: 30.0},
    base_rate_kg_ha=150.0,
    rates_by_zone={1: 150.0, 2: 80.0, 3: 0.0},
    price_per_kg=45.0,
)
```

Аргументы `base_rate_kg_ha` и `price_per_kg` сохранены для совместимости с
шаблоном из Word. При `unit="l"` они означают л/га и руб./л соответственно.
Имена файлов используют дату с подчёркиваниями `YYYY_MM_DD`.

## Пакетная обработка и контроль площади

Передайте папку `data/zones/`, которую формирует Модуль 2. Генератор найдёт
датированные маски, создаст комплект на каждую дату и `season_summary.json`.
Сводка позволяет проверить постоянство суммарной площади между датами.
Допуск задаётся `--area-tolerance-ha` (по умолчанию 0.01 га). Проверяется
разница максимальной и минимальной площади. При одной успешной дате
`area_stable` равен `null`: сравнить её с другой датой нельзя.
Ошибки отдельных файлов записываются в `errors`; остальные даты продолжают
обрабатываться. Повторные даты в одной входной папке отклоняются до экспорта.
CLI возвращает код `1` при ошибках, `2` при превышении допуска площади или неполном покрытии эталона и `0`
при успешной обработке без таких расхождений.

В одном пакетном запуске должны находиться даты **одного поля**. Площадь
считается по валидным пикселям классов 1–3. В текущем М2 облачные участки внутри
поля получают класс ближайшей зоны; эти пиксели включаются в предписание и
экономику. Это восстановленная классификация, а не прямое наблюдение.
Если во входной маске всё же остались nodata/0, М3 их не заполняет и исключает
из расчёта. Исходное покрытие и восстановленная площадь записаны М2 в
`index_stats_*.json`: `observed_area_ha`, `filled_area_ha`, `filled_percent`.

Для демонстрации пакетного режима есть отдельный генератор **синтетических**
масок на шесть недель:

```powershell
python src/module3/examples/create_demo_season.py
```

Он сохраняет входы, предписания и сводку в
`data/module3_demo/synthetic_season/`. Файл `PROVENANCE.json` явно указывает
происхождение данных. Это проверка работы программы, а не наблюдавшаяся история поля.

## Границы применения

Классы Модуля 2 относительные: низкий индекс не устанавливает причину стресса
и не доказывает потребность в конкретном препарате. Нормы `150 / 80 / 0` из ТЗ
используются для учебной демонстрации. Реальные нормы и решение о внесении
задаются агрономом для конкретной культуры и препарата.

GeoJSON и ESRI Shapefile — готовые геопространственные файлы стандартных
форматов. Их пригодность для конкретного бортового компьютера проверяется по
документации производителя: могут потребоваться определённая CRS, название
поля нормы или дополнительный формат задания. Без указания модели оборудования
и проверки импорта нельзя заявлять совместимость со всеми тракторами.
## Реальный сезон и интеграция с M4 (28.10.2026)

Из корня проекта установите зависимости M2 и M3:

```powershell
python -m pip install -r src/module2/requirements.txt -r src/module3/requirements.txt
python src/module3/examples/run_real_season.py
```

Скрипт проверяет совпадение сеток и полного контура восьми сцен с эталоном
`data/samples/sample_zones.tif`, запускает M2 и сохраняет предписания в
`data/prescriptions/`. Используется актуальное заполнение классов облаков в М2.
На всех восьми датах площадь предписания 79,6 га; 18 июля 4,12 га восстановлены
по соседним зонам. Индексы в облачных пикселях остаются без наблюдения.
Скрипт сохраняет аудит `input_coverage.json`. Успех — код 0; код 2 означает
изменение площади или неполное покрытие, код 1 — ошибку обработки.

Если маски M2 уже готовы:

```powershell
python -m pip install -e src/module3
python -m vra run data/zones -o data/prescriptions --reference-mask data/samples/sample_zones.tif
```

Новый необязательный аргумент Python API — `reference_mask_path`.
Положительные валидные пиксели эталона задают полный контур поля, а его классы
не используются для назначения норм. Сетка, CRS и размеры должны совпадать.
В `coverage` каждого отчёта записываются `reference_field_area_ha`,
`unclassified_area_ha`, `unclassified_pixel_count`, `coverage_percent`,
`is_complete`, `economics_scope`. `season_summary.json` содержит `incomplete_dates`.
Без эталона полная площадь неизвестна и блок coverage не создаётся.

`total_field_area_ha` сохраняет прежний смысл — сумма площадей классифицированных
зон, а не полная кадастровая площадь. Вся экономика относится именно к этой
площади, включая классы, восстановленные М2. Полнота `coverage` не означает
отсутствие облаков на исходной сцене. Оставшиеся неизвестными пиксели в маске
не получают нормы. Их отсутствие в задании не определяет поведение машины
вне полигонов; неполное задание требует отдельного решения команды.

Для режима kg добавлены `base_rate_kg_ha`, `price_per_kg`, для l —
`base_rate_l_ha`, `price_per_l`. Старые `base_rate`, `price_per_unit` сохранены.
В zone_breakdown добавлен точный `rate_factor` (null при нулевой базе).

Сопутствующие изменения `src/module4/app.py`: чтение новых и старых полей,
точный пересчёт без округления коэффициентов, отрицательная экономия при
перерасходе, предупреждения о неполной классификации и восстановлении в М2.
Финансовый KPI отображается с двумя десятичными знаками. При изменении норм
скачивание старых файлов отключается; изменение только цены его не блокирует.
Кабинет явно отказывает в показе литровых предписаний как килограммовых.
При нулевой исходной базе нормы зон фиксированы, ползунок меняет только базу
сравнения. Проверка слайдера не создаёт новых GeoJSON/Shapefile автоматически.

Проверка кабинета на подготовленных данных:

```powershell
python -m pip install -r src/module4/requirements.txt
python src/module3/examples/verify_real_season.py
python -m streamlit run src/module4/app.py
```

`verify_real_season.py` проверяет геометрию и покрытие экспорта, совпадение
экономики M3/M4, восемь дат × пять слоёв через Streamlit AppTest и блокировку
скачивания при изменении нормы. Дополнительно проверяет сценарий 200/100/0
кг/га, базу 200 и цену 50 руб./кг через новые и старые имена JSON. Результат — `data/prescriptions/verification.json`.
Внешние спутниковые тайлы не входят в автоматические проверки.


## Сводка готового сезона без векторизации

```python
from vra.batch import build_season_summary
summary = build_season_summary("data/prescriptions", zones_dir="data/zones",
                               failed={}, upstream={})
```

Функция возвращает словарь в схеме `run_series`, не записывает файлов и не
запускает векторизацию. Сохранение `season_summary.json` выполняет вызывающий
код. `zones_dir` рекомендуется: тогда отсутствие metrics для ожидаемой даты
попадает в errors. Без него набор дат определяется по `metrics_*.json`.
`failed` — ошибки М3; `upstream` — ошибки М2 текущего запуска. Ключи дат
допускают YYYY-MM-DD и YYYY_MM_DD. Даже при наличии старого metrics эти даты
исключаются из records. Ошибка без старой маски также учитывается в dates_found.
Пустой каталог даёт 0 дат и area_stable=null; это не успешный прогон сезона.
Повреждённый JSON, неверная дата, нечисловая площадь или отсутствующий экспорт
попадают в errors; остальные даты продолжают обрабатываться. Функция не может
сама определить свежесть снимка: вызывающий код обязан передать ошибки
переобработки. Старые файлы она не удаляет.

В `main_pipeline.py` прежняя season_summary оставлена тонкой обёрткой для
совместимости, сама сводка строится М3. Формат успешного результата сохранён.

Для текущего демонстрационного поля эталон остаётся
`data/samples/sample_zones.tif`: используются только положительные пиксели
контура, не классы. При уточнении западной границы М1 надо согласованно обновить
эталон и пересчитать все даты. Для другого поля нужен его собственный эталон.

Персональная инструкция MODULE3_START_HERE.md убрана из корня репозитория;
командные команды запуска находятся в этом README.
