# Модуль 1, КТ3: слои для кабинета и сквозной конвейер

Критерий КТ3: при запуске `main_pipeline.py` сырые данные со спутника проходят весь путь до готовых файлов
Модуля 3, а кабинет Модуля 4 получает растровые слои без ошибок. Проверено 28.10.2026 на сезоне 2026
(8 дат, 07-03 … 08-24).

## Что сделано

| Файл | Зачем |
|---|---|
| `main_pipeline.py` (корень) | М1 → М2 → М3 → слои для новых дат, проверки, `pipeline_report.json` |
| `src/module1/s2fetch/overlays.py` | PNG-слои NDVI, NDRE, MSAVI, NDMI (из растров М2), RGB (из сцен), HIDDEN; `overlays/meta.json`; CLI `python -m s2fetch.overlays` |
| `src/module1/s2fetch/pipeline.py` | `fetch_series()` возвращает результаты по датам (`written` / `exists` / `error`); `run()` и CLI без изменений |
| `src/module1/s2fetch/manifest.py` | манифест не перезаписывается, если изменилось только время запуска |
| `src/module1/tools/check_m4.py` | кабинет М4 через `streamlit.testing.v1.AppTest`: все даты × слои; копия без `indices/*.tif` |
| `src/module1/tools/overlay_map.py` | `overlays/overlay_check.html`: подложка Esri, контур поля, полигоны М3, PNG одной даты |
| `src/module1/tests/test_overlays.py`, `test_main_pipeline.py` | тесты слоёв и конвейера |

## Как работает `main_pipeline.py`

1. **М1.** `s2fetch.fetch_series` по `--start`/`--end`, по умолчанию одна сцена на ISO-неделю (`--no-weekly`
   отключает). Сцены — в `<data>/scenes`, эталон сетки — `data/samples/sample_scene.tif`. С `--skip-fetch`
   этап пропускается, и `.env`, pystac-client, s2cloudless не нужны.
   Без пакетов М1 или ключей CDSE этап М1 падает до обращения к сети одной строкой-подсказкой без трейсбека. Ошибка `*M1_fetch` пишется в отчёт, остальные этапы идут по уже скачанным сценам, код выхода 1.
2. **М2.** Обычно `process_new_scenes` (только новые даты). Вся серия через `run_pipeline` запускается, если:
   - сцена уже обработанной даты изменилась (sha256 не совпал с `pipeline_state.json`): так закрыта ловушка
     `s2fetch --force`, которую `process_new_scenes` не видит;
   - новая дата раньше уже обработанной;
   - задан `--rebuild`.
   Если файла состояния нет, а результаты М2 уже лежат, им доверяем: хэши сохраняются, в отчёт пишется
   предупреждение.
3. **М3.** `generate_prescription(..., reference_mask_path=data/samples/sample_zones.tif)` для дат, которые М2
   обработал в этом запуске. Ещё он запускается для дат, где маска зон изменилась, нет `metrics_*.json`
   или поменялись нормы и цена. `season_summary.json` собирается из `metrics_*.json` без повторной
   векторизации. Схема совпадает с `vra.batch.run_series` побайтно, это проверяет тест.
4. **Слои.** `s2fetch.overlays.build_overlays` по всем датам, кроме упавших в этом запуске. Если входы и
   параметры не менялись, файлы не трогаются.
5. **Проверки:**
   - `check_outputs` М2;
   - `season_summary.area_stable` и отсутствие неполных дат;
   - CRS, transform и размер у `scenes`, `zones`, `indices`, `hidden_stress` такие же, как у `sample_scene.tif`;
   - `meta.bounds` покрывают рамку `field_boundary.geojson`;
   - рамки GeoJSON предписаний покрывают её с допуском 10 м;
   - все PNG одного размера.
6. **Отчёт** `<data>/pipeline_report.json` и сводка в консоль. Код выхода: 0 — ок, 1 — ошибки обработки,
   2 — проверки не прошли.

Дата, упавшая на этапе, дальше не идёт; остальные даты обрабатываются. Повторный запуск без новых снимков
меняет только отчёт. Если `--data-dir` не `data/`, туда копируется `field_boundary.geojson` (его ищет М4).

## Геометрия и цвета слоёв

- Leaflet растягивает `ImageOverlay` линейно в EPSG:3857, поэтому PNG строится на сетке 3857. Прямоугольник
  охватывает сетку сцен 104×104 (EPSG:32637). Шаг 1,843 м = 10 м × 1,4746 / 8, PNG 846×849.
  Поворот UTM относительно 3857 −0,96°.
- `meta.bounds = [[47.378900, 40.293093], [47.388419, 40.307102]]`.
- Каждый выходной пиксель берёт пиксель сцены, в который попал его центр (nearest). Края пикселей 10 м
  ступенчатые с шагом 1/8 пикселя, без размытия.
- RGB — снимок, а не тепловая карта: alpha 255, растяжка одна на три канала и на сезон — перцентили 2…98
  отражения B04, B03, B02 по пикселям поля всех дат (0,0242…0,0880), гамма 1,3. Параметры — в `meta.rgb`.
  Прежняя растяжка превью КТ2 (0…0,18, гамма 1,6) оставляла поле почти однотонным: всё отражение поля
  лежит в 0,02…0,09. Растяжка по каналам отвергнута: колея и проплешины уходят в пурпур, ранние даты синеют.
  Превью КТ2 (`scenes/preview`) не менялось.
- Палитры `CMAP_VEG` и `CMAP_WATER`, альфа 235 и шкала — по формуле `season_ranges` из `app.py`.
  Тест извлекает константы и функции `colorize`, `season_ranges` из `app.py` через `ast` (без streamlit)
  и сравнивает их результаты с нашими. Шкала сезона: NDVI 0,420…0,908, NDRE 0,213…0,724,
  MSAVI 0,214…0,653, NDMI 0,022…0,459.
- Вне контура alpha 0. Облако или тень внутри контура — серый `[128,128,128,150]` (`--nodata-mode transparent`
  делает прозрачным). Без серого сквозь дыру видна подложка Esri другой даты.

## Ограничения

- Повторный запуск **со скачиванием** длится около 2 мин даже без новых снимков: `s2fetch` заново оценивает
  облачность всех дат интервала (поведение КТ2: выбор недели зависит от всех её дат). С `--skip-fetch` — <1 с.
- `--rebuild` и подмена сцены пересчитывают М2 всей серии (это дёшево, ~0,4 с); более ранние даты дают те же
  файлы.
- Рамка предписаний М3 построена по пикселям (центр внутри контура), поэтому контур поля выступает за неё на
  3,3 м. Это в пределах пикселя, допуск проверки 10 м.
- М4 к слою добавляет `opacity=0.85`: реальная непрозрачность индексов 235 × 0,85, RGB 255 × 0,85,
  серого «нет данных» 150 × 0,85.
- TiTiler (задача D) не делался: ждёт отдельного «ок».
